# 前后端设计交接

本轮需求与架构讨论已收口。前后端依据 [联调约定](../api.md)、[协议基线](wire.md) 和 [架构规划](../architecture.md) 独立开发；协议源、类型和本地 Mock 位于 [contracts](../../contracts/README.md)。

## 设计权限与分工

用户已明确不继续讨论实现细节，同时要求保证前后端可并行开发。因此公共路径、字段、错误码、快照与流式事件已经固定为 v0.1.0 契约，双方共同遵守；算法、存储、配置阈值等内部设计仍交由实现团队。Q33–Q38 的建议数值没有成为产品默认值。

| 范围 | 负责方式 |
| --- | --- |
| HTTP 资源、字段、鉴权和业务错误 | 按同一 OpenAPI 实现；调整先共同更新契约 |
| WebSocket 事件、流式关联、快照与增量时序 | 按现有事件 Schema 和协议说明实现 |
| 页面状态、排队和失败提示、重连体验 | 前端设计，后端提供所需状态及错误信息 |
| 插件接口、执行上下文、队列和取消实现 | 后端按分层架构设计，对外行为与联调契约保持一致 |
| 资料与消息校验、昵称占用、重入细则 | 后端负责实际判定并返回声明的配置与错误；前端按同一结构处理 |
| 队列限制、超时、限频、冷场与邀答参数 | 前后端确定并记录配置及前端可观察结果 |
| 创建和加入的重复提交处理、凭证初始化 | 按引导凭证、成员凭证和 membershipId 的契约实现 |

这些设计无需继续向用户逐项询问；如需改变已确认的产品范围、成员权限或可见性，则作为产品需求变更处理。
部署、容量验证目标和服务重启恢复继续按已约定范围暂缓，具体小游戏玩法留待后续。

## 共同交付物

1. HTTP OpenAPI：资源路径、Method、鉴权、请求响应、校验、HTTP 状态和稳定业务错误码。
2. WebSocket 契约：连接鉴权、事件 Schema、接收范围、流式开始与终态、序号、快照及恢复时序。
3. 典型交互时序：消息提交与异步回复、串行排队、掉线恢复、退出、移出和关闭房间。
4. 与正式 Schema 一致的示例和 Mock，供两端分别开发与联合验证。
5. 配置与设计说明：记录共同选定的参数、默认值及用户可感知结果。

线上字段在 `contracts/` 中维护单一权威 Schema，类型、校验和 Mock 从中派生；前后端分别放在 `frontend/`、`backend/`，不互相导入内部业务实现。
已有 OpenAPI、公共与事件 Schema、成功错误样例、WS 场景、本地 Mock、检查工具和可生成的 TypeScript 类型。前端和后端业务应用尚未实现；实际业务行为需在实现后按下列场景验收。

## 联调必须覆盖的场景

- 创建、邀请和加入：临时身份复用、人数上限、必填资料、昵称冲突及重复提交。
- HTTP 响应与 WebSocket 事件任意先后到达，同次重试不重复发送聊天或调用 AI。
- 房主 AI 调用 FIFO 串行，自动触发遇忙跳过；AI 未受理时合法聊天仍成功。
- 流式增量归并为同一条回复，完成、失败和取消互斥，部分输出不会因失败丢失。
- 中途加入不接收入房前已开始回复的片段、全文或快照累计文本；当前话题单独公开。
- 原成员重连先取得有权限的快照，再衔接后续增量，避免漏字或重复拼接。
- 多标签页共享身份、名额与限频；关闭单页和主动退出的行为明确区分。
- 房主掉线后已受理调用继续，新的自动触发暂停；超时关房取消剩余调用。
- 被移出身份和已关闭房间不能继续接收数据，关房后清理本产品保存的聊天与公开资料。

后续中大型或跨模块编码仍按仓库规则，先提交 Implementation Plan 并等待确认。
